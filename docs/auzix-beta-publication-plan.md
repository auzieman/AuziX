# AUZiX beta publication plan

AUZiX beta publication should feel like a product shelf, not a naked artifact
dump. The intended public shape is:

```text
https://auzix.auzietek.com/
  index.html        branded AUZiX beta landing page
  repo/             AUZiX package repository
  isos/             public ISO images and checksums
  receipts/         selected build receipts, audits, and release notes
```

Near-term implementation can be simple: an nginx virtual host or location block
serving static content generated by the AUZiX build/publish pipeline.

## Public safety gate

Lab media and public media are different artifacts.

Public ISO publication must strip or regenerate:

- lab SSH authorized keys;
- root/user password hashes that are only for lab testing;
- private hostnames, tunnels, internal API URLs, and BKC-only addresses;
- unreleased screenshots or personal files;
- any build cache that exposes local paths or credentials.

Public package repositories should publish package archives, indexes, checksums,
and selected receipts. They should not publish private build workdirs or raw
runtime secrets.

## Landing page content

The landing page should sit above the repo and ISOs and explain:

- what AUZiX is;
- current beta status;
- known rough edges;
- install notes;
- post-install notes;
- package repository URL;
- ISO download links and checksums;
- build date, git commit, and validation summary;
- links to Auzietek, Linux Users, and community/contact pages.

The current demo story should include:

- strict AUZiX path model with compatibility aliases;
- live ESXi graphical boot;
- Enlightenment desktop landing profile;
- Midori branded start tabs;
- EFL installer/package-manager work;
- package repo growth;
- Podman/container proofs;
- BusyBox and Nginx micro container wins.

## Community and social links

Use the controlled Auzietek community/contact page rather than hardcoding raw
Discord invite links throughout generated artifacts. Discord links are useful
but brittle because visitors may need login, app handoff, or a fresh invite.

Public pages may link directly to LinkedIn where appropriate:

- `https://www.linkedin.com/in/auzieman`

## Install-time direction

The next installer-shaped ISO should land in the branded desktop state, then
offer a clear guided path:

1. choose disk/layout;
2. choose simple package groups;
3. install base system;
4. configure users/network/desktop;
5. enable package repo;
6. install selected post-install packages;
7. reboot into the installed AUZiX desktop.

Package groups should stay simple at first:

- base;
- desktop;
- browser/internet;
- office/productivity;
- development;
- media/art;
- containers/podman;
- retro/amiga-lab later.

## Pipeline shape

Recommended pipeline stages:

1. build package repo;
2. build lab ISO;
3. run lab validation;
4. build public ISO from the same recipe with public-secret stripping enabled;
5. validate public ISO contents;
6. publish to `auzix.auzietek.com/repo`, `.../isos`, and `.../receipts`;
7. update landing page metadata.

The current `scripts/publish-auzix-package-repo.sh` already handles package repo
index/checksum publication to a static directory. The beta shelf should wrap
that instead of replacing it.
